# Workflow ownership

Use this contract when substantial work crosses phases or specialists. It is not a required presentation format.

1. Keep the requested outcome, current acceptance criteria, unresolved issues, and authorized scope in view. Follow-ups normally refine that state; an explicit new request or stopping point changes it.
2. Choose one primary workflow. Bring in a specialist only when its concrete procedure improves the next decision or check.
3. Use existing context before asking. Make safe assumptions explicit when useful; ask a focused question when the missing fact materially changes correctness, risk, or direction.
4. Advance the actual deliverable. If evidence rejects an approach, revise or replace it within scope. Preserve requested coverage rather than silently shrinking the result.
5. Verify the relevant outcome with the smallest meaningful check, broadening for risk. A repeated failure calls for new evidence or a new theory, not another identical attempt.
6. Integrate specialist findings. A child review, draft, or checkpoint does not finish an authorized parent implementation. Conversely, a review request does not authorize code changes.
7. Finish when the requested result and its relevant checks exist, or explain the exact missing input/access that prevents progress. Respect explicit approval gates, budgets, and user-owned verification boundaries.

Use native collaborators only when the current task and runtime permit them and a bounded independent contribution is useful. The primary owner integrates and verifies the result. User-owned tasks are not a substitute for subagents.

Keep the process internal unless an update helps the user. Do not require numbered phase announcements, a scorecard, an interview, or a workflow-name handoff for routine work.
